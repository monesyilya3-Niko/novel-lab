# 增量 PRD — novel-lab GUI 数据持久化 + 稳定性 + 可维护性升级

> 产品经理：许清楚
> 文档类型：**增量 PRD**（基于 `docs/PRD_gui_workbench.md` + `docs/DESIGN_gui_workbench.md`，只描述「变更部分」）
> 上游现状：阶段一已交付「全功能可视化工作台」，但数据层仍是**内存扫描 + JSON 散落**的临时方案。
> 本次目标：把 GUI 数据层从「脆弱的内存/文件扫描」升级为「长期稳定、可维护、可扩展」的持久化架构。

---

## 0. 变更摘要（一句话）

**novel-lab GUI 的数据层从「内存索引 + 散落 JSON」升级为「SQLite 关系索引 + 版本化迁移 + 常驻服务」**，在**零第三方依赖、老数据无损迁移**的前提下，获得稳定持久、可 SQL 统计、AI 易维护的能力。

---

## 1. 变更背景与目标

### 1.1 为什么做这次升级（阶段一遗留的痛点）

| # | 阶段一现状（痛点） | 具体表现 | 本次要解决 |
|---|---|---|---|
| 痛点 1 | **索引脆弱**：`asset_index.py` 是纯内存扫描缓存（TTL 5s），每次失效全量 `glob` + `stat` + `json.loads` | 资产一多就慢；缓存随时失效；无法跨进程/跨重启持久 | 引入 SQLite 索引，一次建库、增量更新、持久可查 |
| 痛点 2 | **kind 靠文件名后缀硬编码**（`_SUFFIX_KIND` 常量） | 加新资产类型要改代码；`genre-prose-card-index.json`、`trope-library.json` 这类「非卡片」资产当前根本不被识别 | 资产「实体」入库，kind 成为数据字段而非代码常量 |
| 痛点 3 | **服务绑定 AI 会话不稳定**：`_BOOKS` / `_runtime` 是进程内 `dict` | 服务重启后已导入的书、分析进度全部丢失；`gui_state/` 目录当前为空（状态没真正落盘） | 分析进度、书元数据落 SQLite，重启可恢复 |
| 痛点 4 | **数据散落 JSON，难统计扩展** | 「某题材有多少卡片」「某书关联哪些报告」这类关系查询要么扫目录、要么查不了 | 建关系模型，支持 SQL 统计 |
| 痛点 5 | **无 schema 版本化/迁移机制** | 以后加字段、加模块，改数据结构就可能破坏老数据 | schema 版本号 + 幂等迁移脚本 |

### 1.2 三个升级目标（正交）

| # | 目标 | 说明 | 可衡量标准 |
|---|---|---|---|
| G1 | **稳定持久** | 服务重启/电脑重启后，资产索引、分析进度、书元数据不丢、可恢复 | 重启后 `get_overview`/`get_status` 返回的数据与重启前一致 |
| G2 | **可统计扩展** | 用户「增加数据」后能查、能看、能按题材/类型/书做关系查询 | 支持按 kind / 题材 / 书 ID 的 SQL 查询与统计 |
| G3 | **AI 易维护** | 代码分层清晰、文档齐全、迁移脚本幂等可回滚，改字段不破坏老数据 | 加一个字段只需改一处 + 一条迁移，老数据自动升级不丢 |

> 铁律三约束：后端禁用第三方包。`sqlite3` 是 Python 标准库，合规。此方案不引入任何 pip 依赖。

## 3. 需求池（P0 / P1 / P2）

> P0 = Must have（本次必须交付）；P1 = Should have；P2 = Nice to have。编号「持久化模块-序号」。

### 3.1 数据持久化层（SQLite）

| 编号 | 需求 | 优先级 | 说明 / 验收 |
|---|---|---|---|
| P0-1 | SQLite 单文件库作为**索引 + 关系 + 元数据**的权威存储 | P0 | 库文件落在项目内（如 `gui_state/index.db`）；纯 `sqlite3` 标准库，零第三方依赖 |
| P0-2 | **资产 JSON 实体保留原文件**，SQLite 只存「索引 + 元数据 + 关系」，不把 JSON 大字段塞进库 | P0 | `assets/*.json` 原样不动；库中存 path/kind/元数据，详情仍读原 JSON |
| P0-3 | 资产实体入索引：书 / 资产卡（voice/structure/commercial/craft）/ 题材包 / 文风卡 / trope 库 / 报告 全部可识别 | P0 | 现有 55 资产 + 8 报告（含 `trope-library.json`、`genre-prose-card-index.json`）迁移后全部可被 `list_assets` 命中，不再靠文件名后缀猜 |
| P0-4 | 资产 ↔ 书的关联关系入库 | P0 | 能查「某书产出了哪些资产/报告」「某题材有多少卡片」 |
| P0-5 | 分析进度/任务状态落库（替代进程内 `_runtime` 的易失部分） | P0 | 服务重启后 `get_status` 能恢复上次的 cursor / 批状态 |

### 3.2 老数据迁移（关键，不可破坏）

| 编号 | 需求 | 优先级 | 说明 / 验收 |
|---|---|---|---|
| P0-6 | **幂等迁移**：迁移脚本可重复执行，重复跑不产生重复数据 | P0 | 连续跑两次迁移，库中记录数不变 |
| P0-7 | **可回滚**：迁移前备份原 SQLite（若有）与快照，失败可回退 | P0 | 迁移脚本 `--rollback` 或备份文件可恢复 |
| P0-8 | **完整性校验**：迁移后校验「资产数、报告数、书数」与迁移前一致 | P0 | 迁移日志输出 `migrated=N, assets=55, reports=8`，与源目录对账一致 |
| P0-9 | **迁移可重复对账**：提供 `migrate --check` 只读校验，不写库 | P1 | 校验发现缺失/多余时明确报错 |

### 3.3 服务常驻方案

| 编号 | 需求 | 优先级 | 说明 / 验收 |
|---|---|---|---|
| P0-10 | **命令行常驻**：`python -m gui.server`（或等价入口）前台/后台常驻运行 | P0 | 启动后进程保持存活，服务不随请求结束而退出 |
| P0-11 | **开机自启脚本**（Windows，本项目当前环境）：可选安装/卸载 | P1 | 提供 `.bat`/任务计划注册脚本；用户可一键开/关自启 |
| P0-12 | 优雅关闭：收到退出信号时刷盘 SQLite + 保存进度 | P1 | 强杀不丢已提交数据（SQLite 事务保证 + 关闭钩子） |

### 3.4 schema 版本化 + 迁移脚本

| 编号 | 需求 | 优先级 | 说明 / 验收 |
|---|---|---|---|
| P0-13 | `schema_version` 字段 + 迁移脚本链（`migrations/0001_*.sql` 等） | P0 | 启动时自动检测版本，按序执行缺失迁移 |
| P0-14 | 迁移**幂等 + 事务**：每条迁移在单事务内执行，失败自动回滚 | P0 | 中途失败不留半成品状态 |
| P0-15 | 加字段/加模块 = 加一条迁移，不动老数据 | P0 | 未来扩展只需新增迁移文件 |

### 3.5 数据统计 / 查询能力

| 编号 | 需求 | 优先级 | 说明 / 验收 |
|---|---|---|---|
| P0-16 | `get_overview` 改由 SQL 聚合（替代内存 `count_by_kind`） | P0 | 首页 KPI 走 SQL，无需全量扫描 |
| P0-17 | 资产按 kind / 题材 / 书 ID 筛选与分页（SQL WHERE + LIMIT/OFFSET） | P0 | `list_assets?kind=&genre=&book_id=` 支持组合筛选 |
| P0-18 | 关系统计查询：某书关联报告/资产、某题材卡片计数 | P1 | 提供统计 API 或复用筛选结果 |
| P0-19 | 全文/元数据检索（书名、题材名模糊匹配） | P2 | `LIKE` 或 `FTS`（标准库 `sqlite3` 自带 FTS5，可选） |

## 4. 数据模型需求（产品视角，非 SQL）

> 以下描述**需要哪些实体、什么关系**，具体表结构/SQL 由架构师设计。

### 4.1 核心实体

| 实体 | 说明 | 关键属性（产品语义） | 对应现状 |
|---|---|---|---|
| **书（Book）** | 一本已导入/已拆的书 | 书名、book_id（稳定）、源路径、题材（genre）、导入时间、拆书状态 | `corpus/*.txt` + 报告的 book_id 前缀 |
| **资产（Asset）** | 任意一份资产实体 | kind（voice/structure/commercial/craft/genre_pack/prose_card/trope/…）、名称、文件路径、所属书（可空）、题材（可空）、mtime、大小 | `assets/*.json` 55 个 |
| **报告（Report）** | 拆书报告 / 笔法分析 | 类型（book/craft）、所属书、文件路径、字数、生成时间 | `reports/*.md` 8 个 |
| **分析任务/进度（AnalysisTask）** | 一次拆书/分析的状态 | book_id、status（pending/running/paused/done/error）、cursor、批状态摘要、时间戳 | `gui_state/*.json`（当前为空，需从内存落库） |

### 4.2 核心关系

| 关系 | 方向 | 说明 | 支撑的需求 |
|---|---|---|---|
| 书 → 资产 | 1 对多 | 一本书产出多份资产卡 | 「某书产出了哪些资产」 |
| 书 → 报告 | 1 对多 | 一本书有拆书报告 + 笔法分析 | 「某书关联哪些报告」 |
| 题材 → 资产 | 1 对多 | 一个题材（genre）有多张文风卡/题材包 | 「某题材有多少卡片」 |
| 书 → 分析任务 | 1 对多（或 1 对 1） | 一本书的历史/当前分析进度 | 断点续传、重启恢复 |

### 4.3 边界与约束

- **资产实体内容（JSON 大字段）不落库**，SQLite 只存索引 + 元数据 + 关系；详情按路径读原文件。理由：避免 JSON 大文本塞进 SQLite 导致膨胀与冗余，保持「单文件小库 + 实体文件」分离。
- **书正文（章节全文）不落库**，仍按现有「正文按需读文件」策略。
- `kind` 从「代码硬编码常量」提升为「数据字段」，但**仍需白名单校验**（防路径穿越），新增 kind 需在迁移中登记。
- 数据文件位置：SQLite 库建议放 `gui_state/`（该目录当前为空，天然是「状态」落点）。

## 6. 架构影响（增量，简要）

> 沿用「路由 → 服务 → 适配/索引」分层，**新增一个持久化层**，不改范式：

1. **新增 `gui/db.py`（或 `gui/persistence.py`）**：SQLite 连接管理 + schema 初始化 + 迁移执行。纯 `sqlite3` 标准库。
2. **改造 `asset_index.py`**：从「内存扫描缓存」改为「SQLite 查询为主 + 文件扫描为迁移/增量同步源」；`kind` 判定从 `_SUFFIX_KIND` 硬编码改为读库。
3. **改造 `state_store.py`**：分析进度从 `gui_state/*.json`（或内存）落 SQLite，保留 JSON 文件作为兼容/降级。
4. **新增 `gui/migrations/`**：版本化迁移脚本目录。
5. **新增 `gui/server.py` 入口 + 自启脚本**：命令行常驻 + 开机自启。
6. **新增迁移 CLI**：`python -m gui.migrate`（执行/对账/回滚）。

## 8. 交付边界

- **本次交付（P0）**：SQLite 持久化层 + 资产/书/报告/进度实体入库 + 老数据幂等迁移与对账 + 命令行常驻 + schema 版本化迁移框架 + 基于 SQL 的概览/筛选查询。
- **P1**：开机自启脚本、迁移 `--check` 对账、优雅关闭刷盘、关系统计 API、单实例锁。
- **P2**：目录重排、全文检索 FTS、题材/书名模糊检索增强。

> 本次**不改变**前端交互与可视化（复用阶段一界面），只替换其背后的数据来源（从内存扫描 → SQLite），对外 API 契约（`/api/overview`、`/api/assets` 等返回结构）尽量保持不变，保证前端零改动或极小改动。
