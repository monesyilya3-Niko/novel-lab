# novel-lab 项目规约（硬性要求，任何违反即视为 bug）

> **版本**：v2 ｜ 2026-09-23 ｜ 取代 v1（v1 只有三铁律条文，缺少「如何保证铁律不被绕过」的机制）
>
> **本文件是全项目规则的单一权威来源。** 其它文档（`AGENTS.md` / `README.md` /
> `PROJECT_SUMMARY.md` / `HANDOFF.md`）只允许引用本文件，**不得复制条文或数字**。
>
> 每条规则统一按五要素书写：**条文 / 适用范围 / 判定标准 / 理由 / 预期作用**。
> 「判定标准」必须是**可执行、可复现**的——凡是不能落到代码或命令上的，就不算规则。

# 第一部分 · 三条核心铁律（业务红线）

铁律回答的是「**什么东西必须为真**」。违反它们，产出物即失去意义。

## 铁律一 · 题材隔离

| 要素 | 内容 |
|---|---|
| **条文** | 不同题材的资产/配置严格隔离。聚合题材包时，**本次聚合的 `source_books`** 的 genre 必须全部一致；不一致必须显式失败，**禁止静默跳过**。 |
| **适用范围** | ① 题材包聚合（`pass5_aggregate.py`）；② 资产写入（`craft-card.meta.genre`）；③ 桥段库（每条 trope 的 `genre_scope`）；④ 检索/注入时的题材匹配。**不适用**：`assets/` 目录下同时存在多个题材的资产（这是常态，非违规）。 |
| **判定标准** | ① `collect_books()` 返回 `(books, mismatches)`；`main()` 在 **`--books` 显式指定**时，被点名的书若不属于目标题材（或根本不存在）→ `sys.exit(1)`；未显式指定时，范围外的异题材书**必须打印列出**（不阻断）。② `validate.py` 校验 `craft-card.meta.genre ∈ KNOWN_GENRES`。③ 每条 trope 必须有 `genre_scope`，缺失即硬错误。 |
| **理由** | 题材混淆会让「都市文技法」污染「玄幻文」的写作 prompt，产出物直接失真且难以察觉。**2026-09-23 修正**：原实现只查 `assets/` 下全部 voice-card，导致多题材并存（本项目常态 3 个题材）时 `聚合` 命令**完全不可用**——比条文更严不等于更安全，只是把工具弄坏。现口径与条文对齐：判定对象是 source_books。 |
| **预期作用** | 题材包可被信任为「单题材纯样本」；同时保证 `聚合` 在多题材仓库中可用，且不会出现「以为聚合了 A+B、实际 B 被静默丢掉」。 |

## 铁律二 · 万字报告

| 要素 | 内容 |
|---|---|
| **条文** | 每本书的「拆书报告 + 笔法分析」**合计**字符数 ≥ **10000**（字符数口径，非字节）。不足即阻断交付。 |
| **适用范围** | 所有进入 `reports/` 的交付报告。单份 < 10000 仅 soft warning，最终以**合计**为准。 |
| **判定标准** | ① 单一来源：`scripts/report.py::check_combined_report_length(reports_dir, name)`；纯长度入口 `combined_report_ok(book_chars, craft_chars)`。② CLI：`novel.py 分析` 收尾校验，不足 `sys.exit(1)`。③ GUI：`_generate_reports` 在**写盘前**用 `engine_adapter.combined_report_ok()` 判定，不通过**一个字节都不写**。④ **存量复核**：`novel.py 同步检查` 对 `reports/` 下已有报告逐本复核。 |
| **理由** | 「万字」是交付质量的下限承诺，写进 README 就是对用户的契约。**2026-09-23 事故**：GUI 路径是「先写盘 → 再校验」，校验失败只抑制 `report_ready` 事件、**不删已落盘文件**，导致 4 本不达标报告长期留在交付目录冒充合格品；而校验只在生成时发生，**没有任何机制回头复核**。 |
| **预期作用** | 不合格报告**进不了** `reports/`（写盘前拦截）；已进去的能被 `同步检查` 发现（存量可审计）。 |

## 铁律三 · 纯标准库零第三方依赖

| 要素 | 内容 |
|---|---|
| **条文** | `scripts/` 与 `gui/` 后端**只允许** import Python 标准库。 |
| **适用范围** | `scripts/`、`gui/`（含 `engine_adapter` / `db` / 各 service）。**不适用**：`gui/web/` 前端层（Vite + React 生态正常使用 npm 依赖）、`build/` 打包脚本、`tests/` 中已声明的开发工具。 |
| **判定标准** | ① `tests/test_stdlib_only.py` 全绿（AST 扫描 import 白名单）。② CI 的 `ruff check .` 无新增依赖告警。③ 新增第三方 import 必须在 PR 中显式说明并同步修改白名单与测试——**不得**只改白名单让测试变绿。 |
| **理由** | 「零依赖」是绿色版/安装器能内置运行时的前提，也是用户「解压即用」承诺的基础。已用 `ctypes` 实现 Windows 进程探活——**禁止**引入 `psutil` 等替代品。 |
| **预期作用** | 交付形态（便携包 / 安装器）不需要用户装任何东西；供应链攻击面最小化。 |

# 第二部分 · 六条工程约束（保障铁律不被绕过）

铁律回答「什么必须为真」，工程约束回答「**凭什么相信它真的为真**」。
这一部分全部来自 2026-09-23 总工排查中**实际发生过**的失效——每条都对应一个已复现的事故。

## 约束一 · 校验先于副作用

| 要素 | 内容 |
|---|---|
| **条文** | 任何「校验」必须在**不可逆副作用（写盘/发布/推送）之前**执行。禁止「先写盘、后校验」。 |
| **适用范围** | 报告生成、资产组装、索引写入、任何产出交付物的路径。 |
| **判定标准** | 代码审查：校验调用点必须在 `write_text` / `json.dump` / `publish` 之前。测试：`tests/test_report_write_gate.py`（低于门槛时断言**磁盘零新增**，且不覆盖既有合格文件）。 |
| **理由** | **2026-09-23 事故**：`_generate_reports` 先写盘后校验，失败只抑制事件不删文件 → 4 本不达标报告留在交付目录。同类问题在资产组装上早已修复（改为「内存组装 → 校验 → 通过才落盘」），**报告链路漏了**——说明模式必须写成规则，不能靠记得。 |
| **预期作用** | 校验失败 = 磁盘无变化，可安全重试；不再出现「半成品冒充合格品」。 |

## 约束二 · 运行时路径实时求值

| 要素 | 内容 |
|---|---|
| **条文** | 一切运行时路径必须**在函数内实时求值**（`config.STATE_ROOT / "x.json"`）。**禁止**写成模块级常量。 |
| **适用范围** | `gui/`、`scripts/` 全部模块。 |
| **判定标准** | ① `tests/test_module_config_snapshot.py`：AST 扫描「模块级 `X = config.<路径常量>`」，发现即失败（白名单需附理由，仅 `gui/logging_setup.py`）。② `tests/test_config_isolation.py::TestRuntimePathFollowsConfig`：重定向 `config` 后断言真实文件指纹（存在性+sha256+mtime）不变。③ `tests/test_zz_state_dir_leak_guard.py`：跑完全量测试后真实 `gui/state/` 与 `gui_state/` 不得有新增/改写。 |
| **理由** | **2026-09-23 事故**：`_SETTINGS_FILE = config.STATE_ROOT / "settings.json"` 在**导入期**固化，测试的 `setattr(config, "STATE_ROOT", tmp)` 对它**完全无效**，于是 `tests/test_system_service.py` 写进了**真实**的 `gui_state/settings.json`（受控实验：写入哨兵值 → 跑测试 → 哨兵被抹掉）。`_isolation.py` 的登记表机制只覆盖「通过 config 属性访问」的代码，对导入期快照无能为力。 |
| **预期作用** | 测试隔离真正生效；跑测试不再改写用户真实配置；同类缺陷在提交前被静态拦截。 |

## 约束三 · 索引必须可对账、可收敛

| 要素 | 内容 |
|---|---|
| **条文** | SQLite 索引是派生数据，必须能①**只读对账**出与磁盘的差异，②**收敛**回一致（含删除）。只增不删的索引视为缺陷。 |
| **适用范围** | `gui_state/index.db` 的 `assets` / `reports` 表（`books` 表不在此列——书的存废由业务决定）。 |
| **判定标准** | ① `python -m gui.migrate --check` 返回 `一致: YES`（exit 0）。② `python -m gui.migrate --prune --dry-run` 能列出待清理行。③ `--prune` 清理前必须 `backup()`。④ `tests/test_migrate.py` 的 prune 用例组（清理孤儿行 / dry-run 不写库 / 不动 books / 一致时 no-op）。 |
| **理由** | **2026-09-23 事故**：`run_migrate()` 只有 UPSERT，**从不删除**已消失文件的对应行。删掉 `reports/` 下 8 个文件后，索引仍留着 8 条指向不存在文件的记录——GUI 会列出**幽灵报告**，而 `--check` 只能报告差异、**没有任何手段修复**。 |
| **预期作用** | 索引与磁盘永不失同步；删除操作有配套的收敛路径，不会留下永久漂移。 |

## 约束四 · 规则上线必须回扫存量

| 要素 | 内容 |
|---|---|
| **条文** | 新增或收紧任何硬校验时，**必须同时**：① 提供存量复核手段；② 对既有产物执行一次回扫；③ 明确处置结论（重生成 / 标注历史 / 删除）。 |
| **适用范围** | 铁律级校验、schema 收紧、评分口径变更、阈值调整。 |
| **判定标准** | 提交中同时出现：(a) 门禁代码；(b) 存量复核入口（如 `novel.py 同步检查`）；(c) 回扫结论记录（CHANGELOG）。三者缺一即视为未完成。 |
| **理由** | **2026-09-23 事故（规则时间差）**：铁律二硬校验于 **2026-09-07** 引入，而 chireng / qingning / sangshi 的报告提交于 **2026-09-01**（早 6 天）——校验**只向前生效**，存量产物从未被回扫，于是「规则上线前的产物永久豁免」，且无人知道。这**不是违规**，是规则落地流程缺失。 |
| **预期作用** | 规则收紧后，全仓库的达标状态是**已知**的；不会出现「新规则很严，但旧产物悄悄不达标」。 |

## 约束五 · 交付物只经门禁路径产出

| 要素 | 内容 |
|---|---|
| **条文** | 进入 `assets/` / `reports/` 的交付物，**必须**由受门禁约束的路径产出：`novel.py <子命令>` 或 GUI 服务层。**禁止**在会话/脚本中直接写文件绕过门禁。 |
| **适用范围** | 全部交付目录。会话内 AI 协作、临时脚本、手工修复同样受约束。 |
| **判定标准** | ① 交付物写入点收敛于 `assemble.py` / `pipeline.py` / `report.py` / `report_craft.py` / `services._generate_reports`。② 任何绕过路径产出的文件，必须立即用 `novel.py 同步检查` 复核，不达标则删除。③ 例外情形（如纯会话产出的种子资产）必须在 CHANGELOG 显式标注。 |
| **理由** | **2026-09-23 事故（门禁旁路）**：`Lord_of_the_Mysteries` 的报告提交于 **2026-09-21**，晚于铁律 14 天——它**不是**时间差，而是由会话直接写文件（提交信息为 `session-agent reports`），`novel.py 分析` 与 GUI 两条门禁路径**都没经过**，硬校验从未执行。 |
| **预期作用** | 门禁是「唯一入口」而非「可选入口」；不会再出现「产出于规则之后、却从未被规则检查」的产物。 |

## 约束六 · 文档数字单一来源

| 要素 | 内容 |
|---|---|
| **条文** | 任何「当前实测口径」类数字，**只允许**写在 `AGENTS.md §7`。其它文档**引用**它，不得复制数字。 |
| **适用范围** | `README.md` / `PROJECT_SUMMARY.md` / `HANDOFF.md` / `CHANGELOG.md` 及一切面向人的文档。带日期的历史快照（CHANGELOG 条目）不受此限。 |
| **判定标准** | ① `tests/test_doc_metrics.py`：`AGENTS.md §7` 的测试用例数 / API 端点数 / 版本号必须等于实测；README 不得再出现写死的测试基线。② 新增文档若需引用口径，必须用「见 AGENTS.md §7」而非数字。 |
| **理由** | **2026-09-23 事故（口径漂移）**：同一时期 README 写 782、AGENTS 写 853、`PROJECT_SUMMARY` 正文写 782+55 而页脚写 853+65（**同一文件自相矛盾**）、HANDOFF 写 780/801/55/60，实测 857。而 `AGENTS.md §7` 自己声明「所有数字以实测磁盘为准」——**文档违反了它自己的规则**。手工维护多份重复数字已被证明不可靠。 |
| **预期作用** | 口径漂移从「需要人记得同步」变成「不可能发生」；新增测试会主动提示更新权威口径行。 |

# 第三部分 · 违反判定与处置

| 级别 | 判定 | 处置 |
|---|---|---|
| **P0** | 铁律一/二/三被绕过，或约束一/二/三失效并造成真实副作用 | 立即阻断交付，修复 + 补回归防线（含反向验证） |
| **P1** | 铁律成立但存在绕过路径；或约束四/五/六未执行 | 本次迭代内修复 |
| **P2** | 机制正确但有可改进点（重复实现、长函数、文档滞后） | 触及即清，不集中大扫除 |

**「违反即视为 bug」的判定原则**：

1. **能落到命令上才算违规**——「代码不够优雅」不是违规，「`ruff check` 报错」是。
2. **规则时间差不构成豁免，但也不构成违规**——规则上线前的产物按「约束四」回扫并处置，而不是判它违规。
3. **绕过门禁 = 违规**，无论产出物本身是否达标（达标只是巧合，不可复制）。
4. **防线不得弱化**——修改被锁定的测试断言，必须同时说明「原断言为何不再正确」，并在 CHANGELOG 记录。
