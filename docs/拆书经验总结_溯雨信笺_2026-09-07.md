## 三、完整流程回顾

拆书标准链路（无模型模式，纯本地 JSON 组装）：

```
解码原文 → 采样章节 → pass1(结构) / pass2(角色) / pass3(文风) / pass4(商业) / pass5(技法)
   → python novel.py 组装 <目录名> --genre <题材>
   → python novel.py 校验 assets/<name>-<类型>.json （× 4 类）
   → python novel.py 合规 assets/<name>-voice-card.json corpus/<name>.txt
   → python scripts/report.py ... （拆书报告）
   → python scripts/report_craft.py ... （笔法分析）
```

关键命令清单（本次实际使用）：

```bash
# 组装（name 必须是 corpus/raw/ 下的目录名，不是书名）
python novel.py 组装 suyixinjian_chosen --genre campus-redemption

# 校验四类资产
python novel.py 校验 assets/suyixinjian_chosen-voice-card.json
python novel.py 校验 assets/suyixinjian_chosen-structure-obs.json
```

## 四、遇到的问题 + 根因 + 解决方案

> 共 4 类问题，按发现顺序排列。每一条都标注了「现象 / 根因 / 解决方案 / 预防经验」。

### 问题 1：voice-card 校验硬错误 —— 角色 role 用了「男主」

**现象**
```
dialogue.character_voices[1].role 值 '男主' 不在允许集合
['主角','反派','女主','导师','工具人','配角']
```

**根因**
- voice-card 的 `role` 字段有一个**允许值白名单**，只含 `主角/反派/女主/导师/工具人/配角`，**不含「男主」**。
- 但 `normalize_pass2` 里的排序字典却有 `"男主": 1` 的映射——这个映射**仅用于角色排序**，不参与 schema 校验。两个机制用了两套词汇表，产生了「排序能识别男主、校验却拒绝男主」的认知错位。

**解决方案**
- 在 `pass2_character.json` 中，将男主原溯的 `"role": "男主"` 改为 `"role": "主角"`。
- 重新组装后，voice-card 校验 PASS。

**预防经验**
- 写角色 role 时，**永远只用白名单里的 6 个词**。男性主角 → 「主角」，女性主角 → 「女主」，不要写「男主」「男二」「女配」等非白名单词。
- 排查此类错误时，先 grep 校验代码里的「允许集合/白名单」字面量，再对照排序字典，区分「排序用词」与「校验用词」。

### 问题 2：voice-card 校验警告 —— emotion_handling.examples 为空导致 REJECT

**现象**
```
emotion_handling.examples 为空——建议补充情绪写法示例 → REJECT
```

**根因**
- `normalize_pass3` 提取情绪示例时，调用的是 `extract_emotion_examples(pass3, mode)`。
- 该函数**只从 pass3 顶层**的 `switching_rules`（list）/ `anti_pattern`（dict）/ `banned` 三个键提取，通过 `_find_key` 递归查找关键词命中即返回原值。
- 它**不读** `emotion_handling.examples` 这个嵌套键——所以即便我在 `emotion_handling.examples` 里写了示例，也被无视，导致 examples 为空。

**解决方案**
- 在 `pass3_style.json` 的**顶层**（`narration` 之前）新增两个键：
  - `switching_rules`：list，每条含 `scene / mode / example_pattern`（如愤怒→动作外化式、悲伤→体感式、心动→环境投射式）。
  - `anti_pattern`：dict，按情绪给出「避免写法」。
- 重新组装后 examples 非空，voice-card 校验 PASS。

**预防经验**
- **pass3 的情绪示例必须写在顶层 `switching_rules`（list）＋ `anti_pattern`（dict）**，不是 `emotion_handling.examples`。
- 养成习惯：改完 pass 文件后，先看对应 normalize 函数到底读哪个键，再决定数据放哪，避免「写了但读不到」。

### 问题 3：commercial-obs 校验 3 条可选字段警告 —— 字段层级放错

**现象**
```
⚠ commercial-obs 缺少 'skeleton'（可选变体字段）
⚠ commercial-obs 缺少 'dry_spell_tolerance'（可选变体字段）
⚠ commercial-obs 缺少 'common_mistakes'（可选变体字段）
结论: WARN（可入库，建议人工复核）
```

**根因**
- `validate.py` 的 `COMMERCIAL_OBS_VARIANT_FIELDS = ("skeleton", "dry_spell_tolerance", "update_rhythm", "retention_risk_points", "common_mistakes")` 要求这 5 个字段在 **commercial-obs 顶层**。
- `assemble_obs` 的实现是**透传** pass4 的非 `_` 前缀顶层键，不做任何嵌套展开。
- 我之前把 `skeleton` 写进了 `payoff_density.payoff_types[]` 里、把 `dry_spell_tolerance` 写进了 `payoff_density` 里、把 `common_mistakes` 写进了 `opening_analysis` 里——层级全错了，顶层自然找不到。

**解决方案**
- 在 `pass4_commercial.json` 顶层补入三个字段（对齐参考书格式）：
  - `skeleton`：**字符串**，多阶段叙事骨架（第一阶段…第二阶段…第三阶段…）。
  - `dry_spell_tolerance`：**字符串**，如 `"3章（约9000字）"`。
  - `common_mistakes`：**字符串**，编号列表（`1.…；2.…；3.…`）。
- 重新组装后 commercial-obs 从 WARN 升为 PASS。

**预防经验**
- **commercial-obs 的 5 个可选变体字段必须放顶层**，类型分别是：`skeleton`/`dry_spell_tolerance`/`common_mistakes` 为字符串，`update_rhythm` 为 dict（含 `chapters_per_day` + `burst_timing`），`retention_risk_points` 为 list（每条含 `position/reason/mitigation`）。
- 写 pass4 前先对照一本已 PASS 的参考书（如 `assets/chireng_chosen-commercial-obs.json`）看顶层键结构，一次写对，避免返工。

### 问题 4：笔法分析报告字数不足 —— 技法缺 deep_analysis 深度字段

**现象**
```
⚠ 报告字数 5600 < 硬门槛 10000，深度分析不足，阻断交付 → sys.exit(1)
```

**根因**
- `report_craft.py` 的字数主要来自 craft-card 里每条技法的 `deep_analysis`（7 个深度字段）。
- 但 pass5 产出的 20 条技法**都没有 `deep_analysis`**，导致 7 段深度内容全空，报告只有 5600 字，不达单份 10000 门槛。

**解决方案**
- 重写 `pass5_craft.json`，为全部 20 条技法补上 `deep_analysis`，7 个字段齐全：
  - `reader_psychology`（读者心理机制）
  - `execution_steps`（执行步骤）
  - `applicable_scene`（适用场景）
  - `usage_boundary`（使用边界）
  - `intensity_control`（强度控制）
  - `combo_patterns`（组合套路）
  - `migration_checklist`（迁移清单）
  - 每字段 100-200 字高质量中文分析。
- 关键：`assemble.py` 的 `assemble_craft_card` 在 `if "craft_analysis" in pass5:` 分支是**透传**整个 `craft_analysis`，**不截断** technique 的 deep_analysis——所以深度内容必须由 Pass5 直接写进 pass5_craft.json，本地 `deep_analyze.py` 只校验、不补内容（遵循「AI 不编造数据」红线）。
- 重新组装 → 重新生成报告后：笔法分析从 5600 → **20625 字符**，与拆书报告合计 **25344 字符**，远超铁律二门槛。

**预防经验**
- **pass5 写技法时，每条都必须带 `deep_analysis` 7 字段**，这是万字报告字数的来源，不能省略。
- ✅ **口径已统一（方向①·真·合计口径，2026-09-08 深度检查后修复）**：PROJECT_LAW 铁律二条文与执行机制现已一致——「拆书报告 + 笔法分析 **合计** ≥10000」。执行机制改为：合计校验收敛到 `novel.py 分析` 一键命令（读取两份报告合计判定，不足即 `sys.exit(1)`）；`report.py` / `report_craft.py` 单份脚本只做 soft warning（单份不足只提示、不阻断）。当前合计 25344 字符 PASS。

### 问题 5：craft-card 合规 2 条 WARN —— 引号内方法论口诀被误判为原文引用

**现象**
```
硬错误 0 条，警告 2 条
  ⚠ 引号内片段 23 字 > 20 → WARN 人工复核 @ craft_analysis.pov_control.techniques[1].deep_analysis.execution_steps …视觉定基调、听觉增氛围、触觉/味觉/嗅觉做点睛…
  ⚠ 引号内片段 21 字 > 20 → WARN 人工复核 @ craft_analysis.tension_building.peak_valley_pattern …铺垫蓄力→小爆发→缓冲回暖→再蓄力→大爆发…
结论: WARN（无硬错误，建议人工复核后入库）
```

**根因**
- `compliance.py` 的规则是：**引号内的连续片段超过 20 字即触发 WARN**（防原文大段引用）。
- craft-card 的 `deep_analysis` 里写了大量**方法论口诀**（如"视觉定基调、听觉增氛围…"、"铺垫蓄力→小爆发→缓冲回暖…"），这些是拆书总结出的**写作规律，不是从原文抄录的句子**。
- 但这些口诀恰好用了引号包裹、且长度超过 20 字，被合规器误判为「疑似原文引用」。

**结论（准确口径）**
- **voice-card 合规：PASS**（0 硬错 0 警，46,846 个 12-gram 窗口 0 原文引用）。
- **craft-card 合规：WARN**（0 硬错 2 警）。这 2 条警告**不是真正的原文泄露**，而是拆书方法论口诀被长度阈值误伤，**无需修改资产内容，可正常入库**。

**预防经验**
- craft-card 的 deep_analysis 是「写作规律总结」，天然会包含带引号的口诀式表述，合规时出现 1-2 条「引号内 >20 字」的 WARN 属正常现象，人工确认非原文抄录即可。
- **表述口径务必区分**：voice-card 合规 PASS 与 craft-card 合规 WARN 是两个独立结论，不能笼统写成「合规 PASS」。

## 五、可复用经验清单（写给下一本书）

1. **role 用词**：只用 `主角/反派/女主/导师/工具人/配角`，男主人设写「主角」。
2. **pass3 情绪示例**：写顶层 `switching_rules`（list）＋ `anti_pattern`（dict），别写进 `emotion_handling.examples`。
3. **pass4 商业字段**：5 个可选变体字段放顶层；`skeleton`/`dry_spell_tolerance`/`common_mistakes` 用字符串，`update_rhythm` 用 dict，`retention_risk_points` 用 list。
4. **pass5 技法**：每条必带 `deep_analysis` 7 字段，否则笔法分析字数不够。
5. **写 pass 前先对照参考书**：打开一本已 PASS 的同类型资产（chireng/qingning/sangshi），照它的顶层键结构和字段类型写，一次写对。
6. **组装 name 参数**：`python novel.py 组装 <目录名>` 里的 name 必须是 `corpus/raw/` 下的目录名，不是书名。
7. **回归验证闭环**：每次改 pass 文件后，必须「重新组装 → 重新校验 → 重新生成报告」三步走完，不要只改文件不回归。
8. **AI 不编造数据**：所有缺失数据留空待填，本地脚本只做校验与装配，绝不代填内容（尤其财务类、深度分析类）。
