# 产品需求文档（PRD）— 书籍分析 GUI 工具

> novel-lab 拆书系统「可视化外壳 / GUI 前端层」

---

## 0. 项目信息

| 项 | 内容 |
|---|---|
| 文档语言 | 中文 |
| 产品名称 | novel-lab 书籍分析 GUI 工具（可视化前端层） |
| 项目归属 | novel-lab（Python 3.13 纯标准库拆书系统） |
| 产品定位 | novel-lab CLI 的「可视化外壳」，**不是独立新产品**。后端引擎（novel.py 拆书 / QC 质检 / LLM 写作 / 模型配置）全部保留，GUI 仅负责调用与展示 |
| 窗口形态 | Web 界面：本地服务 + 现代浏览器前端（点启动脚本自动弹浏览器） |
| 前端技术栈 | Vite + React + MUI + Tailwind CSS（构建产物静态托管） |
| 后端服务 | Python 标准库 `http.server`（零依赖，**不违反 novel-lab 三铁律**） |
| 导入格式 | txt（P0 主线）、epub（P1 增强） |
| 续传粒度 | 双层：外层「章」导航 + 内层每章切 N 个「批次」，断点精确到「第几章第几批」 |

### 原始需求复述

1. 可打开、可操作的图形界面
2. 导入并展示整本书的内容
3. 支持分段、分批次地进行分析（一本书文字量大，无法一次性全处理）
4. 长文本的拆分
5. 进度展示
6. 断点续传机制

## 1. 产品定义

### 1.1 Product Goals（3 个清晰正交目标）

| # | 目标 | 说明 | 可衡量标准 |
|---|---|---|---|
| G1 | **降低使用门槛** | 让不懂 CLI 的用户通过图形界面完成「导入→分段→分析→查看结果」全流程，无需记忆命令 | 新用户 5 分钟内完成首次导入并启动分析 |
| G2 | **可视化长文本与任务状态** | 整本书内容可流畅浏览；分析任务进度、每章每批状态一目了然 | 单章 10 万字级文本滚动流畅（虚拟滚动）；进度实时刷新 |
| G3 | **可靠的分批处理与断点续传** | 任意时刻中断（关窗口/断网/模型报错）后，可从「第几章第几批」精确恢复，不重复计算 | 中断后恢复 ≤ 1 个批次的重复工作量；状态持久化到磁盘 |

### 1.2 目标用户与核心场景

| 用户角色 | 核心场景 | 核心诉求 |
|---|---|---|
| 拆书作者 / 内容创作者 | 导入一本书，拆解结构、提炼人物/文风/商业要素，用于二创或学习 | 想看到整本书、分段跑分析、能保存进度 |
| 编辑 / 校对人员 | 批量分析多本书，监控拆书/QC 进度 | 任务队列、进度条、可中断续跑 |
| 技术尝鲜用户 | 想体验 novel-lab 但不会命令行 | 图形化操作、默认配置开箱即用 |

## 2. 用户故事（覆盖导入/展示/分批/进度/续传）

1. **导入**：作为拆书作者，我想要把一个 `.txt`（或 `.epub`）文件拖入窗口并看到它被正确解析成「章节列表」，这样我能确认书已完整导入、章节切分正确。

2. **展示**：作为创作者，我想要在窗口内流畅浏览整本书（含 10 万字级长章节），并能定位到任意章节，这样我能在分析前快速核对内容。

3. **分批**：作为用户，我想要把每一章自动切成可配置大小的「批次」，并能手动调整/重切某章批次，这样我能避免单次请求超出模型上下文限制。

4. **进度**：作为用户，我想要看到「整体进度 + 每章每批的状态（待处理/处理中/成功/失败）」，这样我能随时掌握分析进行到哪。

5. **续传**：作为用户，我想要在关掉窗口或分析中断后，重新打开能从「第几章第几批」继续，而不是重头再来，这样长书分析不会白跑。

6. **结果查看**（延伸）：作为创作者，我想要在界面中直接查看每章/每批的分析产出（结构卡、人物卡、文风卡等资产），而不是去翻文件目录。

## 3. 技术规范

### 3.1 需求池（P0 / P1 / P2）

#### P0（Must have — 首版必备）

| 编号 | 需求 | 说明 / 验收标准 |
|---|---|---|
| P0-1 | **GUI 启动** | 点击启动脚本 → 本地 `http.server` 起服务 → 自动弹默认浏览器打开前端；关闭即停 |
| P0-2 | **txt 导入** | 拖拽/选择 `.txt` → 后端读文件 → 复用 `sampler.split_chapters()` 切章 → 前端展示章节列表 |
| P0-3 | **整本书展示 + 长文本渲染** | 前端用虚拟滚动（TanStack Virtual）渲染章节内容，10 万字级章节滚动流畅、可章节跳转 |
| P0-4 | **章切分复用后端** | 章切分直接调用 novel-lab `sampler.py` 的 `split_chapters` / `detect_volumes`，保证与 CLI 一致 |
| P0-5 | **批次切分（新增薄封装）** | 每章按可配置参数（如单批最大字符数 / 单批最大 token 估算）切成 N 批；切分参数可配置 |
| P0-6 | **分批分析执行** | 后端按「章→批」顺序调用 novel-lab `pipeline.py` 拆书流水线（采样→量化→Pass1-5→组装→校验），前端可触发/暂停 |
| P0-7 | **进度展示** | 实时展示：整本书进度条 + 章列表（每章含 N 批状态徽标） |
| P0-8 | **断点续传（双层）** | 复用 `state_tracker.py` 的 `_tracking-state.json` + `state_revision` 机制；断点精确到「第几章第几批」；重启后自动识别并从中断批继续 |
| P0-9 | **状态持久化** | 分析状态（章/批状态、已产出资产索引）落盘（JSON/SQLite），重启不丢 |

#### P1（Should have — 重要但可后置）

| 编号 | 需求 | 说明 |
|---|---|---|
| P1-1 | **epub 导入** | 用 EbookLib 解析 EPUB2/3，抽取正文+章节结构；注意 EbookLib 为 AGPL-3.0，需评估许可影响（或仅作为可选/插件化引入） |
| P1-2 | **失败重试** | 单批失败可手动/自动重试，复用 pipeline 已有的「JSON 解析纠错重试（3 轮）」 |
| P1-3 | **结果查看面板** | 结构化展示每章产出：结构卡/人物卡/文风卡/商业卡/聚合卡，前端渲染 JSON 资产 |
| P1-4 | **模型配置界面** | 图形化复刻 `model_config.py` 的 11 个预设（deepseek/siliconflow/moonshot/zhipu/dashscope/openai/anthropic/ollama/lmstudio/vllm/custom）与路由 |
| P1-5 | **批次手动调整** | 用户可对某章重新切分 / 手动改批大小 |

#### P2（Nice to have — 增强）

| 编号 | 需求 | 说明 |
|---|---|---|
| P2-1 | **批量导入多本书** | 队列式管理多本书的分析任务（参考 `batch.py` 的 `run_book`） |
| P2-2 | **导出分析报告** | 一键导出 Markdown/JSON 汇总报告 |
| P2-3 | **暗色主题 / 自定义** | 阅读体验优化 |
| P2-4 | **任务日志/审计** | 查看每批的请求日志、token 消耗统计 |

### 3.2 关键接口对齐（复用现有后端）

| 后端模块 | 复用点 | GUI 调用方式 |
|---|---|---|
| `sampler.py` | `split_chapters()` / `detect_volumes()` 章切分 | 后端路由 `POST /api/import` → 返回章节列表 |
| `pipeline.py` | `run_pass()` / `build_user_input()` 拆书流水线 | `POST /api/analyze/chapter/<idx>/batch/<bidx>` |
| `state_tracker.py` | `_tracking-state.json` + `state_revision` + `apply_transaction` | 作为续传权威状态层，GUI 每次批完成写事务 |
| `llm_client.py` | `chat()` / `resolve_model()` / `DEFAULT_ROUTES` | GUI 透传 task → 模型路由 |
| `model_config.py` | 11 个模型预设 | GUI 复刻配置界面，读写同一配置文件 |

## 4. UI 设计要点

### 4.1 导航结构（左侧栏）

```
[导入书籍]          ← 入口：拖拽/选文件
[章节列表]          ← 章导航（含卷分组），每章显示 N 批 + 状态徽标
[内容阅读器]        ← 当前选中章/批的正文（虚拟滚动）
[分析进度]          ← 整本书进度 + 章×批状态矩阵
[分析结果]          ← 结构化资产卡查看（结构/人物/文风/商业/聚合）
[模型配置]          ← 11 预设 + 路由配置（P1）
[设置]             ← 批次切分参数、服务端口等
```

### 4.2 主要面板

| 面板 | 布局要点 |
|---|---|
| **章节列表面板** | 左侧树状列表：卷 → 章 → 批；每章右侧显示「批数 + 完成批数/总批数」徽标；章已全部完成标绿、部分完成标黄、失败标红 |
| **内容阅读器面板** | 中央主区：虚拟滚动渲染当前章正文；顶部章节标题 + 定位；支持「上一章/下一章」与跳转 |
| **分析进度面板** | 顶部整本书总进度条（完成批数/总批数）；下方表格/矩阵：行=章，列=批，单元格色块表状态（灰=待处理/蓝=处理中/绿=成功/红=失败/黄=跳过） |
| **分析结果面板** | 选中某章后展示该章各批产出的资产 JSON 结构化渲染；支持折叠展开 |
| **启动/控制条** | 底部或顶部：`开始分析` `暂停` `继续(续传)` `重试失败批` 按钮 + 当前状态提示 |

### 4.3 断点续传交互

- 用户关窗口后重开 → 前端请求 `GET /api/status` → 后端读 `_tracking-state.json` 返回「第 X 章第 Y 批」为当前断点 → 前端高亮该批并显示「继续分析」按钮。
- 点击「继续」→ 从中断批开始顺序跑，跳过已成功批（幂等，不重复计算）。

## 5. 桌面壳方案对比（GitHub 调研）

> 结论：**推荐 Python 标准库 `http.server` + 浏览器前端**，零依赖、不违反 novel-lab 三铁律。下表列出各候选以便决策留痕。

| 方案 | 技术栈 | 打包体积 | 许可证 | 是否违反「纯标准库」铁律 | 结论 |
|---|---|---|---|---|---|
| **http.server（标准库）** | Python stdlib | ~0（无额外依赖） | PSF | **不违反** ✅ | **推荐** |
| Electron | Node + Chromium | 100–200MB+ | MIT | 违反（引入庞大 Node/Chromium） | 不采用 |
| Tauri | Rust + 系统 WebView | <10MB | MIT/Apache | 违反（需 Rust 工具链 + 系统依赖） | 不采用 |
| Wails | Go + 系统 WebView | ~几 MB | MIT | 违反（需 Go 工具链） | 不采用 |
| PyWebView | Python + 系统 WebView | ~10–30MB | BSD | 违反（引入 pywebview 依赖） | 不采用 |
| NiceGUI | Python + FastAPI + Vue3 | 轻量 | MIT | 违反（引入 FastAPI/Vue 依赖） | 不采用 |
| PyQtWebEngine | Python + Qt WebEngine | 大 | GPL/LGPL | 违反（引入 PyQt，且 GPL 许可风险） | 不采用 |
| .NET MAUI | C#/.NET | 大 | MIT | 违反（技术栈偏离 Python） | 不采用 |

| 11 | **virtual-scroller** | github.com/valdrinkoshi/virtual-scroller | ~1k | Apache-2.0 | Web Components 虚拟滚动 | 低（备选） | 前端层，不影响 |
| 12 | **novel-lab state_tracker.py** | （本地项目） | — | 自有 | 事务式状态追踪 + state_revision | 高（**续传直接复用**） | 自家代码 |

**关键结论**：
- 长文本渲染 → **TanStack Virtual**（无头、支持动态行高，最适合正文）。
- 续传 → **直接复用 novel-lab 自带 `state_tracker.py`**，不引第三方。
- epub → EbookLib 能力足够，但 **AGPL-3.0 许可需法务/维护者确认**，故列为 P1 且建议插件化/可选引入。
- 桌面壳 → 全部引入依赖均违反三铁律，唯一不违反的是标准库 `http.server`，故最终推荐。

## 7. 关键待确认问题清单

| # | 问题 | 影响 | 建议默认值 |
|---|---|---|---|
| Q1 | 批次切分默认粒度（按字符数还是按 token 估算？） | 决定单批是否超模型上下文 | 默认单批 ≤ 4000 字符（约 2000–3000 token 估算），可配置 |
| Q2 | epub 引入 EbookLib 的 AGPL-3.0 许可是否可接受？ | 决定 epub 是否上线 | 先 txt，epub 待许可确认后插件化 |
| Q3 | 状态持久化用 JSON 文件（复用 state_tracker）还是 SQLite？ | 影响并发与查询 | 沿用 `_tracking-state.json`（与现有架构一致），SQLite 仅 P2 |
| Q4 | 分析任务是否支持并发多章/多批跑？ | 影响 token 消耗与 API 限流 | 首版串行（章内批串行，章间可选串行），并发为 P2 |
| Q5 | 前端构建产物如何托管？（随项目提交 dist 还是启动时 `npm run build`） | 影响安装体验 | 提交预构建 dist，启动脚本直接托管，用户无需装 Node |
| Q6 | 服务端口固定还是动态？ | 影响多实例 | 默认 8000，可配置，被占用则 +1 递增 |
| Q7 | 未配置外部模型时的「AI 接管模式」是否也要在 GUI 体现？ | 影响首版范围 | P0 仅支持已配置模型的分析；无模型提示走 CLI（P2 再补 GUI） |

## 8. 交付边界（首版范围声明）

- **包含**：GUI 启动、txt 导入、章节展示（虚拟滚动）、章+批切分、分批串行分析、双层断点续传、进度展示、失败批重试（P1）。
