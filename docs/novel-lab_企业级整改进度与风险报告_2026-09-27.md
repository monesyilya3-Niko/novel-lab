## 4. 门禁体系与本地复现

CI（`.github/workflows/ci.yml`）三条腿，本轮**逐条本地复现**，不假设「本地绿 = CI 绿」：

| CI 作业 | 步骤 | 本地复现结果 |
|---|---|---|
| `python`（windows × py3.13） | `ruff check .` | EXIT 0 ✅ |
| | `coverage run run_tests.py` + report | 951 通过 ✅（**无 fail-under，报告仅存档**） |
| `python-cross-platform`（ubuntu × 3.11/3.12/3.13） | `ruff check .` + 全量测试 | 逻辑上同源；本轮专门核过跨平台敏感点（见下） |
| `frontend` | `eslint src` / `vitest run` / `tsc -b && vite build` / Playwright e2e / **dist freshness** | 4 warnings(0 errors) / 37 通过 / 构建通过 / dist 未变动 ✅ |

### 本轮专门排除的跨平台隐患

1. **`LICENSES` 与换行符**：新增的归因守卫若断言文件**字节数**，会在 ubuntu checkout（LF）与 Windows 工作区（CRLF）之间产生分歧 → 核查结论：守卫全部用 `assertIn` 子串断言，`1081` 只出现在文档正文的「核实方式」描述里，**与换行符无关**。
2. **资产清单匹配**：`THIRD_PARTY_NOTICES.md` 的逐卡登记断言使用硬编码 `assets/` 正斜杠 + 文件名，不用 `os.path.join`，跨平台一致。
3. **索引与资产变更**：本轮改了 32 个资产 JSON（补 `provenance.copyright`），若索引记录内容校验和会导致对账失败 → 核查结论：全仓库 `hashlib` 仅用于任务 ID 生成，**索引不含 checksum**，改动安全。
4. **`dist` freshness**：`gui/web/index.html` 强制 `eol=lf` 后，Windows/ubuntu 构建产物与仓库内 `dist` 一致；本轮 `vite build` 后 `git status` 干净。

### 一个需要澄清的机制（避免误解）

CI 步骤名为「Iron rule 3 guard (stdlib-only)」看起来像有专门的静态守卫，**实际上它是被动机制**：CI 只安装 `ruff`/`coverage`，不装第三方运行时依赖，因此任何非标准库 import 都会在全量测试中直接 `ImportError` 暴露。本轮新增的 `scripts/genre_registry.py` 只依赖 `pathlib`/`json`，已被该机制覆盖。

## 5. 治理决策记录（为什么这么做）

工程质量的核心不是「改了什么」，而是「为什么这样改、为什么不那样改」。下列决策均已落进代码注释或 CHANGELOG，避免后人重估：

| 决策 | 理由 | 落点 |
|---|---|---|
| 题材清单**由磁盘派生**，不建 `config/genres.json` | 配置文件会成为**第二个真相源**，把漂移从「代码 vs 磁盘」换成「配置 vs 磁盘」 | `scripts/genre_registry.py` 注释 |
| `CORE_GENRES`(3) 与 `KNOWN_GENRES`(34) **分裂为两集** | craft 卡校验只用全链路题材，避免为 32 个 prose-only 题材造假阳性 | 同上 |
| `provenance` 从 warn **升级为 err** | 32 张卡长期无人填 `copyright` 就是「软约束失效」的实证；MIT 合规不能靠自觉 | `validate.py` + 守卫 |
| `B023` 重构而非 `# noqa` 压制 | 经核验**当前不是 bug**（闭包未逃逸循环），但引用延迟绑定是隐患；重构消除之 | `sampler.py::_sentence_at` |
| `zip` **分成 strict=True/False 两类** | `zip(xs, xs[1:])` 天然差一，一刀切开 strict 会立刻误报 | 7 处逐个注释 |
| `UP` 与 `F401` **必须同步应用** | 注解迁到内置容器后 `from typing import` 全成未使用导入，只跑 UP 会让门禁当场报 52+ 失败 | `pyproject.toml` 注释 |
| `dist` 假脏**改源模板 eol**，不给产物打补丁 | 产物换行风格继承自源模板（`gui/web/index.html`），源头不统一治不好 | `.gitattributes` 注释 |
| **推翻**「移除 console.log」审计项 | 实测仅 3 处，两处是 SSE 帧解析失败诊断、一处是 `componentDidCatch` 标准写法，删除会让故障静默 | `CHANGELOG` Known Issues |
| **推翻**「B023 是真 bug」的暗示 | 实测闭包每轮立即调用、未逃逸，属隐患非故障，措辞必须准确 | 同上 |
| `PTH` 永久不启用 | `os.path` 属正当用法，49 处纯风格迁移只制造 diff 噪音 | `pyproject.toml` 注释 |

## 6. 遗留问题清单（按优先级，含证据与处置方案）

### P1-1 前端最大资源 1100 KB：echarts 全量打包 【收益最大】

**证据**：`gui/web/dist/assets/echarts-DKI42x5t.js` = **1100 KB**（`dist` 总计 1.76 MB，占比 63%），比 `vendor`(440 KB) 还大 2.5 倍。

**已完成的诊断**（边界可穷尽证明，非抽样）：

- echarts 相关文件**仅 7 个**：`theme.ts`、`QcVisuals.tsx`、`charts/{BaseChart,BarChart,PieChart,GaugeChart,RadarChart}.tsx`
- 实际 series 类型**恰好五种**：`bar`(3 处)、`heatmap`、`gauge`、`pie`、`radar`
- 需要的组件：`tooltip`、`legend`、`grid`、`visualMap`、`markLine`、`radar` 坐标系
- 全部 echart 用法经 `BaseChart` 中转；`optionOverride` **调用点为 0**（这个「开放口子」实际从未被使用）
- 根因：`BaseChart.tsx:5` 使用 `import * as echarts from 'echarts'`（全量 barrel）

**结论修正**：审计清单说的「echarts 懒加载」**已成立**——`index.html` 只 preload `index`+`vendor`，echarts chunk 随 `AnalysisView` 动态分离。真正的缺口是**体积**：用户一进分析页就要下载 1.1 MB。

**方案**：改为 `echarts/core` + `use([BarChart, PieChart, GaugeChart, RadarChart, HeatmapChart, TooltipComponent, LegendComponent, GridComponent, VisualMapComponent, MarkLineComponent, RadarComponent, CanvasRenderer])`，并保留 `locale: 'ZH'` 行为（需核实 locale 注册路径）。预期 **1100 KB → 350~450 KB（约 −60%）**。

**风险（必须正视）**：漏注册组件在 echarts 中**多数表现为静默不渲染**，不抛错；而本项目单测明确用桩件替换了 echarts（`HomeDashboard.test.tsx`、`QualityWorkbench.test.tsx` 注释所述），**单测抓不到这类回归**。因此改动的正确顺序是：**先补一条「图表确实渲染出 canvas」的 e2e 断言，再改代码**。

**工作量**：1~2 小时（含验证）。

### P1-2 主题 token 债：71 处硬编码色值 / 15 个文件

**证据**：`gui/web/src` 下硬编码 hex 合计 **71 处，分布在 15 个文件**；而真正 `import theme` 的**只有 3 个文件**（`App.tsx`、`AnalysisResultView.tsx`、`charts/BaseChart.tsx`）。最集中的是 `QcVisuals.tsx`（14 处）、`MarkdownReport.tsx`（7 处）、`ProgressPanel.tsx`（6 处）。

**特别值得注意**：`QcVisuals.tsx` 的 `LAYER_COLORS` 注释自称「与 palette 图表色板一致」，但**取值是手抄的副本**——这与本轮修掉的 `launch.py` 平行列表、`chapter_check.py` 权重多源是**同一类缺陷**：一致性靠人抄。暗色模式下这类硬编码色可能对比度不足。

**方案**：将 `QcVisuals` / `MarkdownReport` / `ProgressPanel` 等迁移到 `theme.ts` 的统一色板（`chartDefaults(isDark)` 已提供图表色板入口），并按「暗色适配风险」排序处理。

**风险**：低（纯视觉），但需视觉回归；仓库已有 `docs/screenshots/{home-light,writing-dark}.png` 可作基线。

**工作量**：3~5 小时。

### P1-3 覆盖率有报告、无门禁

**证据**：`.github/workflows/ci.yml` 含 `coverage report`，但**不含 `--fail-under`**；仓库**无 `.coveragerc`**。本地 `coverage` 已安装，可实测。

**影响**：覆盖率可以无声下滑而 CI 全绿；新增代码无最低覆盖要求。「有度量、无门禁」等于没有约束力。

**方案**：先跑一次基线覆盖率并记录，再以「不低于基线」为起点设置 `fail-under`（一步到位设高值会导致长期红灯，反而促使他人绕过门禁）。

**工作量**：1 小时。

### P1-4 eslint 4 条警告

**证据**：`npm run lint` → `4 problems (0 errors, 4 warnings)`，规则为 `react-hooks/set-state-in-effect`，示例位置 `src/state/AppContext.tsx:171`（`refreshStatus().then(...)` 在 effect 内 setState）。

**影响**：目前不阻断 CI，但 effect 内直接 setState 可能造成额外渲染或状态级联；更关键的是**警告长期存在会被无视**，掩盖将来新增的真问题。

**方案**：逐条判定——若属初始水合，用 `useSyncExternalStore` 或显式豁免 + 写明理由；不接受「因为麻烦就留着」。

**工作量**：1~2 小时。

## 8. 建议路线图（有序，每步附理由）

| 步骤 | 动作 | 理由 | 预估 |
|---|---|---|---|
| 1 | **推送 `feat/enterprise-hardening` 到 `origin`** | 8 个提交承载全部 P0 成果但仅存本机，属单点故障；推送是最廉价的防灾 | 5 分钟 |
| 2 | 补一条「图表渲染出 canvas」的 e2e 断言 | 单测用桩件替换了 echarts，**这是 echarts 改动唯一的安全网** | 1 小时 |

| 4 | 覆盖率基线 + `fail-under` 门禁 | 把「有度量」变成「有约束」；先基线后门禁，避免长期红灯 | 1 小时 |
